# Protobuf conformance

The runner and fixtures target [protobuf v36.2](https://github.com/protocolbuffers/protobuf/releases/tag/v36.2)
(stable release published 2026-09-17). The runner uses upstream's Bazel 8.6.0.
This does not upgrade ScalaPB's published protobuf runtime dependency.

```sh
conformance/build_test_runner.sh
sbt "conformanceJVM2_13/test; conformanceJVM2_13/assembly"
conformance/run.sh
```

The build verifies the release archive's SHA-256, uses a private temporary
source directory, and defaults to two build jobs. `CONFORMANCE_BUILD_JOBS` and
`CONFORMANCE_RUNNER_DIR` override those defaults. `CONFORMANCE_OUTPUT_DIR`
selects the report directory (default `target/conformance-results`). CI caches
the versioned runner and uploads reports even on failure. Bazelisk, a C++17
compiler, curl, tar, and sha256sum are required.

## Fixture provenance and prerequisites

`src/main/protobuf/conformance.proto` comes from upstream `conformance/`;
`test_messages_proto{2,3}.proto` come from `src/google/protobuf/`.
The protocol now uses `FailureSet.test` / `TestStatus`, including failure
messages. The testee returns an empty failure set; all expected failures remain
reviewable in the checked-in lists.

There is one explicit proto2 adaptation: the new `GroupField` extension cannot
be generated by current ScalaPB (`printExtension` throws `Not supported`).
`upstream/group-extension.patch` restores its upstream declaration. Apply it
after adopting [groups PR #2272](https://github.com/scalapb/ScalaPB/pull/2272)
(commit `39909b71` plus its shared Editions prerequisite), then regenerate the
conformance fixtures and rerun both suites. That integration has not been
validated on this branch. #2272 does not resolve group text semantics or binary
recursion limits; retain the corresponding limitations until separately verified. Ordinary group fields are
retained. Do not suppress their failures or claim group-extension coverage.

`upstream/editions/` preserves the unmodified upstream 2023 conformance schema
and the proto2/proto3 migration fixtures from `editions/golden/`. These are
outside `PB.protoSources` until the separate Editions generator implementation
supports their features, including DELIMITED message encoding. Dispatch explicitly
skips all four Editions message types, including upstream's unstable edition.
The runner explicitly sets `--maximum_edition 2023` (upstream defaults to legacy
syntax), so the stable Editions cases are executed and their skips stay visible.
The JVM is launched with `-Xrs`: upstream times out a test with SIGQUIT, which
otherwise dumps Java threads and leaves the timed-out process running.

Move the supported schemas into compilation, register their companions and JSON
types, and replace the skip assertions when the implementation lands. Do not
route Editions requests through the legacy proto2/proto3 companions: their
feature semantics differ.

## Regression tests and triage

`ConformanceScalaSpec` exercises protocol dispatch and compares parsed Java
messages with ScalaPB round trips (duplicate scalars, unknown fields, mixed
packed/unpacked fields, malformed input). The Java oracle is generated from the
same fixtures with the project's pinned protoc/runtime. It compares semantic
messages, not serialization order. These tests do not assert that the project's
Java runtime is v36.2; the independent C++ runner supplies the v36.2 oracle.

`PortableWireRegressionSpec` lives in runtime's shared test sources and runs
unchanged on JVM, JS, and Native. Small regressions that do not require Java or
JSON should go there; add Java comparisons to the conformance suite where useful.

```sh
sbt 'runtimeJVM2_13/testOnly scalapb.PortableWireRegressionSpec'
sbt 'runtimeJS2_13/testOnly scalapb.PortableWireRegressionSpec'
sbt 'runtimeNative2_13/testOnly scalapb.PortableWireRegressionSpec'
```

Keep exact test names in failure lists, grouped by observed limitation. Never
copy all failing tests into the lists without reviewing their diagnostics.
The runner fails on unexpected failures and stale expected failures, so fixes
in the groups, enums, UTF-8, JSON/text, and other parser work must remove their
now-passing entries. Framing and recursion-limit changes belong to their own
workstreams; this PR does not change their policies.

The binary/JSON refresh found 46 additional failing cases relative to the old
list, including three renamed FieldMask cases. They are classified in the list
by observed behavior, not wildcarded: JSON coercion/duplicates/unknown enums,
Unicode, well-known types, structural depth and uint64 exponent bounds; binary
oversized tags, MessageSet, and mixed-wire unknown-field ordering. The tag cases
reach the project's Java `CodedInputStream.readTag`; unknown-field ordering is
lost when fields of different wire types share a field number. These are
existing runtime/dependency limitations exposed by the newer runner, not parser
changes in this infrastructure update. The JSON baseline is the published
`scalapb-json4s` 1.0.0-alpha.1, **not** json4s master. Its separate limits,
base64, and NullValue fixes must be released/adopted before removing the
corresponding expectations. The separate UTF-8 work updates
`protobuf-runtime-scala` for JS/Native; the C++ runner here exercises JVM only.

The text refresh adds 113 precise expectations: group names/extensions and Any
syntax; enum reflection and unknown enum numbers; comma/semicolon separators
between fields; required commas in repeated lists; float suffixes/radices and
negative zero; and ignoring reserved names. Representative cases were rerun
with verbose request/response output and checked against `Parser`/`AstUtils`.
Existing unknown-field printing and Unicode-escape limitations remain. The
runner rejects stale expectations, so this baseline must shrink as fixes land.

Related work: [ScalaPB #2270](https://github.com/scalapb/ScalaPB/pull/2270)
and [json4s #675](https://github.com/scalapb/scalapb-json4s/pull/675). Those
resource-limit changes do not imply all the syntax/semantic limitations above
are fixed. In particular, json4s changes require a release and dependency uptake.

## Validated baseline

Full v36.2 run on this baseline (Scala 2.13/JVM):

| Suite | Successes | Editions skips | Expected failures | Unexpected failures |
| --- | ---: | ---: | ---: | ---: |
| Binary/JSON | 2761 | 2832 | 56 | 0 |
| Text | 308 | 464 | 137 | 0 |

Eight conformance unit tests pass, including Java comparisons. The three shared
wire regressions pass on JVM, JavaScript and Native. Expected failures are
limitations, not passing conformance cases; Editions skips are not Editions
implementation coverage.
